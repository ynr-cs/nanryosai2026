# 設計計画書 更新・修正履歴 (Changelog)

本ドキュメントは、南陵祭2026 POS・モバイルオーダーシステム 設計計画書および関連ドキュメントの更新・修正履歴を記録したものです。
これからも随時修正が加わるため、修正番号ごとに内容を追記します。

## 修正1 (2026年5月25日)

これまでの設計上の議論と決定事項、およびそれに伴い各章（第1章〜第13章）へ反映した修正内容。

### 1. SOKタイムアウト時の受付番号とステータス
* **判断**: SOKの仮注文タイムアウト時点では受付番号はまだ発行されていないため、受付番号は `null` のままで問題ない。また、SOK仮注文タイムアウト時のメインステータス（pendingは存在しない）についても `null` 等で処理し、SOK特有のステータス変更のみで対応する。
* **修正内容**: SOK仮注文がタイムアウト（5分経過）した際の処理について、受付番号が未発行のまま破棄される仕様にドキュメントを統一した。

### 2. 店舗（stores）の営業ステータス管理
* **判断**: `isActive`（ブール値）ではなく、文字型（string）で「営業前」「営業中」「営業終了」の3つの状態を管理する仕様にする。
* **修正内容**: `stores` コレクションの営業状況フィールドを `isActive` から `operationStatus` (string) に変更。取り得る値を `preparing`, `open`, `closed` 等の文字列としてドキュメント全体で統一した。

### 3. カート情報の保存先
* **判断**: Firestore等へのカート状態の永続化保存はなくす前提とする。
* **修正内容**: カート情報は「JavaScript変数およびローカルストレージ」でのみ管理する仕様に変更し、サーバーサイド保存の記述を削除した。

### 4. SOK注文の `paymentMethod` パラメータ
* **判断**: SOKの注文フローにはオンライン決済がないため、`paymentMethod` は不要。SOKパラメータは `storeId` 等のみとする。
* **修正内容**: SOK注文作成のAPIパラメータから `paymentMethod` を削除した。

### 5. 放置ペナルティの判定基準時刻
* **判断**: 商品放置によるペナルティ（15分でBAN）の判定基準は、`createdAt` ではなく `readyForPickupAt`（提供準備完了時刻）とする。
* **修正内容**: 第8章や第12章における自動キャンセルおよびBAN処理の基準時間を `readyForPickupAt` ベースに修正した。

### 6. ネガティブ・誤解を招く表現の削除
* **判断**: 先生方からの印象を悪くする「自宅からの注文」「海外からの攻撃」「移行作業中」などの記述はドキュメントから一切排除する。
* **修正内容**: 第13章（付録）や各章のユースケース・セキュリティ項目から該当する記述を完全に削除し、表現を健全なものに修正した。

### 7. `loginVenueAdmin` の扱いについて
* **判断**: この関数は「店舗」ではなく、現在の `main\index.html` に関連する「ステージ発表・催し物会場のリアルタイム情報」のための管理者認証として使用されているものとして扱う。（現時点でのシステム実装は見送り、一旦ドキュメント上の定義のみ修正）
* **修正内容**: 用途を「店舗責任者の二段階認証」から「ステージ発表・催し物会場（venues）の管理者認証」に表記を統一した。

### 8. その他ドキュメントの構成修正
* **第13章の重複削除**: スクリプトや編集の過程で第13章の末尾に同じ内容が二重に記述されていた問題を解消し、一本化してクリーンアップした。
* **表現の微修正**: フォーマッタ等による表記揺れや、「sok-to.html（仮称）」などの仮称表記、不要な「匿名昇格」などの古い表現を取り除き、全体を一貫性のある内容に仕上げた。

## 修正2 (2026年5月25日)

これまでの設計上の議論と決定事項、およびそれに伴い各章（第2章〜第13章）へ反映した修正内容の第2弾。

### 1. 匿名認証の完全廃止とGoogle認証への一本化
* **判断**: SOK利用時等に想定していた匿名認証は完全に廃止し、Google認証に一本化する。ポータル画面 (`portal.html`) は独立してFirebaseを初期化し、共通の `auth.js` は利用しない。
* **修正内容**: 第3章のSOK利用における匿名認証の記述を削除し、認証方式の記載をGoogle認証のみに修正した。

### 2. 受付番号表示とキッチンフローの最適化
* **判断**: SOK画面において受付番号とQRコードを同時に表示している場合、QRコード画面への受付番号併記は不要とする。また、キッチン画面における「調理開始」ボタンは存在せず、注文確定（`createOrder`経由）と同時にキッチン画面に注文が表示され、直ちに調理が開始されるフローとする。
* **修正内容**: 第5章・第6章のSOK画面・シーケンスから受付番号の重複表示を整理し、調理開始ボタンの操作に関する記述を削除した。SOKの仮注文もステータスは `cooking`（`userId != null` でフィルタ）として扱う。

### 3. ファイル配置パスの確定
* **判断**: モバイルオーダー画面およびステータス画面は、`pos/` ディレクトリ配下に置く。
* **修正内容**: ドキュメント全体において、ファイルパスを `pos/mobile-order.html` および `pos/status.html` に統一した。

### 4. モニター画面 (`monitor.html`) の運用方針
* **判断**: モニター画面はデジタルサイネージ的な運用とする。
* **修正内容**: モニターの仕様をデジタルサイネージとしての役割（自動更新・常時表示）を前提とした内容に明確化した。

### 5. 待ち時間の算出主体の変更
* **判断**: 待ち時間の算出は、店舗責任者による手動更新ではなく、Scheduled Functionsによって自動的に算出されるシステムとする。
* **修正内容**: 待ち時間に関する記述を自動算出（Scheduled Functions）を前提としたものに修正し、手動入力の記述を削除した。

### 6. データモデル・ステータスの命名規則統一
* **判断**: ステータス値は厳格に `snake_case` (`cooking`, `ready_to_serve`, `ready_for_pickup`, `completed`, `abandoned`, `cancelled`) で統一する。また、カウンターコレクション名を `receipt_counters` から `counters` に変更する。ユーザーコレクションのFCMトークンフィールドは、配列 (`fcmTokens`) ではなく文字列 (`fcmToken`) とする。
* **修正内容**: 第4章などのデータ定義をはじめ、全章にわたって該当するフィールド名とステータス値を一斉置換した。また、データ整合性のため Firestore Transactions を使用する方針を明記した。

### 7. 注文処理の `createOrder` への一本化
* **判断**: 注文作成ロジックは単一の Cloud Function (`createOrder`) に一本化し、経路は `orderChannel` パラメータで判別する。
* **修正内容**: SOK特有のライフサイクルを廃止し、共通のステータスマシンに準拠するよう、シーケンス図や関数定義を修正した。

## 修正3 (2026年5月25日)

これまでの設計上の議論と決定事項、およびそれに伴い各章へ反映した最終的な修正内容の第3弾。

### 1. SOK注文フローの再構築（関数の3分割と専用ステータス導入）
* **判断**: QRコードを読み取ったユーザーと注文を安全に紐付ける（所有権を確定する）ため、SOK仮注文の作成、ユーザーの割り当て（claim）、最終確定をそれぞれ独立した処理とする必要がある。
* **修正内容**: SOKの注文作成処理を `createSokProvisional`, `claimSokOrder`, `confirmSokOrder` の3関数に分割。また、未確定の注文が厨房画面に表示されるのを防ぐため、メインステータス（`status`）は `null` とし、SOK専用の進行管理フィールド `sokStatus` (`pending`, `claimed`, `confirmed`, `expired`) を新たに導入した。

### 2. タイムアウト処理（Scheduled Functions）の2系統への分離
* **判断**: 「提供準備完了後の受け取り放置（15分）」と「SOK端末での仮注文未確定放置（5分）」は発生理由とペナルティの有無が異なるため、独立したScheduled Functionとして管理・実行するべき。
* **修正内容**: 1分おきに起動する定期実行関数を `abandonStaleOrders`（15分放置・BAN対象）と `expireSokOrders`（5分未確定・BAN対象外）の2つに分割し、それぞれのクエリとステータス更新処理（`abandoned` および `expired`）を明確に定義した。

### 3. Push通知用FCMトークンの複数端末（配列）対応
* **判断**: 同一ユーザーがスマートフォンとPCなど複数の端末でログインし、通知を受け取れるようにする。
* **修正内容**: `users/{uid}` ドキュメントに保存する通知用トークンを、単一の文字列 (`fcmToken`) から配列 (`fcmTokens`) に変更。通知送信側の Cloud Function (`sendOrderUpdateNotification`) も配列内の全トークンに対して送信する仕様に改めた。

### 4. 規約同意日時の保存先最適化
* **判断**: 注文単位だけでなく、ユーザー単位で「初めて規約に同意した日時」を管理・照会できる形が法的・運用的に望ましい。
* **修正内容**: 規約同意時、各 `orders` ドキュメントの `termsAgreedAt` フィールドに記録するだけでなく、`users/{uid}.termsAgreedAt` にも初回同意時のタイムスタンプを保存するフローを追加した。

### 5. SOK仮注文用のFirestoreセキュリティルール特例追加
* **判断**: SOK端末で作成された仮注文は最初は `userId` が `null` であり、QRコード読み取り側のスマホ（未認証または他ユーザー）が内容を取得するためには、読み取り権限の緩和が必要。
* **修正内容**: `orders` コレクションの読み取りルールに、「自身の注文」だけでなく、「SOKの未確定仮注文（`orderChannel == "sok"` かつ `sokStatus == "pending"`）」の場合も誰でも読み取りを許可する条件を追加した。

## 修正4 (2026年5月25日)

複数のAIによる設計計画書の精査・矛盾点抽出レポート（まとめ.md）に基づき、残存していた致命的なシステム制約違反や設計の不整合を解消する最終修正。

### 1. 受付番号発番のトランザクション制限超過リスクの解消
* **判断**: Firestoreの1トランザクションにおける読み取り上限（500回）を超過するループ探索を廃止し、アトミックなカウンターインクリメントに切り替える。
* **修正内容**: 受付番号発番ロジックを、ループによる空き番号検索から、カウンタドキュメント（`counters/receipt_mobile` 等）を用いた `FieldValue.increment(1)` トランザクションによる順次発番に変更した。

### 2. クライアントからのFirestore直接更新の廃止
* **判断**: セキュリティルール（第9章）の要件を正とし、クライアントから `orders` ドキュメントの直接更新は完全に禁止する。
* **修正内容**: 第7章（厨房・提供口）等に記載されていたクライアントからの `update` コード例を削除し、すべてのステータス変更を Cloud Functions（Admin SDK権限）経由での呼び出しに統一した。

### 3. モニター画面（`monitor.html`）のセキュリティルールの特例追記
* **判断**: 認証不要で呼び出し番号を表示する機能要件を満たすため、該当ステータスに限定した公開読み取りルールが必要。
* **修正内容**: Firestoreセキュリティルールに、`status == "ready_for_pickup"` かつ取得フィールドを制限する特例ルールを追加する記述を第9章に追記した。

### 4. 注文ステータス `cooking` の役割分離
* **判断**: 初期状態（未着手）と調理中の状態が同じ `cooking` となり、厨房での区別ができなくなる矛盾を解消する。
* **修正内容**: 新規受付状態を `accepted`（注文確定済み・調理未着手）とし、厨房スタッフが「調理開始」を押下した後に `cooking` に遷移するようにステータスマシンを再設計した。

### 5. ペナルティ時刻の記録フィールド統一
* **判断**: ペナルティによる破棄と通常のキャンセルで集計や追跡を分離するため、記録するフィールドを分ける。
* **修正内容**: 15分放置によるシステム自動破棄時は `abandonedAt` とし、ユーザーやスタッフによるキャンセル時は `cancelledAt` と `cancellationReason` を記録する仕様に統一した。

### 6. データモデル・フィールドの完全一致化
* **判断**: 第4章のデータモデル定義を「真実の単一源泉（SSOT）」として、各章で使用されるフィールド名と完全に一致させる。
* **修正内容**: 
  * 金額フィールドを `totalPrice` に統一。
  * 第6章や第7章のコード例で登場していた未定義フィールド（`paymentMethod`, `paidAt`, `posTerminalId`, `cookingStartedAt`, `createdBy`, `cancellationReason`）を第4章のデータモデル定義表に追記した。

### 7. ファイル配置場所と命名揺れの解消
* **判断**: 第5章と第13章の間で矛盾していたファイルの配置場所や名称を正式決定する。
* **修正内容**: `login.html` と `account.html` をルートディレクトリに、`sok-to.html` 等を `pos/` ディレクトリに明記。また、カウンターのコレクション名を `counters` に統一するなどの表記揺れを全編で解消した。
