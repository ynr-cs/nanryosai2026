ご提示いただいた設計書（第2章〜第11章）を詳細に読み込みました。
「以前の設計構想」「実装後の実態（注記として追記された部分）」「運用マニュアル」が混在しているため、章をまたいだ**仕様の致命的な矛盾や記述の食い違い**が多数発生しています。

具体的に「どこの章のどの部分」が矛盾しているかを、影響が大きい順に10点整理しました。

---

### 1. 厨房画面（kitchen.html）に「有人POSの注文」が表示されなくなる矛盾（致命的）

データ定義と画面の表示条件が噛み合っておらず、**有人POSで受けた注文が厨房に届かなくなる**という致命的な矛盾が発生しています。

- **【第4章 4.5.1】および【第6章 6.5.5】**
- 有人POS経由の注文は、一貫して **`userId: null`** の状態で作成・維持されると明記されています。

- **【第7章 7.3.1（厨房画面の常時購読クエリ）】**
- 厨房画面に注文を表示する条件として、SOKの仮注文を除外する目的で **`where("userId", "!=", null)`** を指定すると記載されています。
- **結果：** このクエリを実装すると、有人POSの注文もすべて除外されて厨房画面に一切表示されなくなります。

### 2. 決済時の「金額照合」を行う画面と運用フローの矛盾

手動QR決済における最重要確認事項である「合計金額の目視照合」を、スタッフがどの画面を見て行うのかについて、実装の実態とマニュアルが乖離しています。

- **【第5章 5.5.4（presenter.html の注記）】**
- 「設計書に記載されていた『注文の合計金額を表示（決済時のスタッフによる目視確認用）』は**実装に見当たらない**。合計金額の表示は `presenter.html` ではなく `monitor.html` の注文確認画面で行われる」と注記されています。

- **【第7章 7.4.2 / 7.6.3】および【第9章 9.11.2】【第10章 10.3.2】**
- マニュアル上では依然として「提供口スタッフが **`presenter.html` 上の合計金額と目視で照合し、『受渡完了』ボタンを押す**」という運用手順が正規ルートとして記載されたままになっています。

### 3. 利用規約同意の「記録場所」と「取得頻度」の矛盾

利用規約に同意した履歴をどこに保存し、毎回確認するかについて、章によって真っ向から対立する仕様が書かれています。

- **【第3章 3.6.3（同意の記録方法）】**
- 「**注文ドキュメント (`orders/{orderId}`)** の `termsAgreedAt` フィールドにタイムスタンプを記録する。（中略）本書執筆時点では**各注文ごとに（毎回）同意を取得**する方針とする」と記載。

- **【第4章 4.5.2（users コレクション）】および【第6章 6.3.4】**
- 第4章では「**`users.termsAgreedAt` のみで管理する。`orders` ドキュメント側には保持しない**」と記載。
- 第6章では「**初回未同意時のみ**同意を取得する方針とする」と記載。

### 4. 注文作成用 Cloud Functions の「関数名」の矛盾

システムの根幹となる注文作成のAPI設計が食い違っています。

- **【第2章 2.5】および【第5章 5.4.2 / 5.4.3 / 5.5.2】**
- 経路ごとに別々の関数（`createOnlineOrder`, `createSokProvisional` または `createOrderFromSok`, `createPosOrder`）を呼び出す設計として記載されています。

- **【第4章 4.6.4 / 4.6.5】および【第6章 6.3.7 / 6.4.5 / 6.5.5】**
- 全経路共通の単一関数 **`createOrder`** を呼び出し、引数の `orderChannel` で内部分岐する設計として記載されています。

### 5. SOK仮注文の「データモデル（sokStatus）」と「確定用関数名」の矛盾

SOKの仮注文をどう管理・確定するかについて、データ定義とセキュリティ制御の前提が崩れています。

- **【第4章 4.5.1】および【第6章 6.4.5 / 6.4.11】**
- 仮注文は単に「`userId: null` かつ `status: cooking`」として作成されると定義されています。（`sokStatus` というフィールドは存在しません）。
- 確定用の関数は `confirmSokOrder` と記載されています。

- **【第9章 9.7.3 / 9.7.4（Firestore セキュリティルール）】**
- 突然、第4章には存在しない **`sokStatus == 'pending'`** や **`sokStatus: "claimed"`** という専用フィールドを用いてアクセス制御を行っています。
- 確定用の関数名も `claimSokOrder` に変わっています。

### 6. BANチェックの「実装場所・実行範囲」の矛盾

ペナルティ対象者かをチェックする処理の実行場所について説明が異なります。

- **【第3章 3.3.1 / 3.5.3 / 3.9 図】**
- BANチェックは「**`login.html`** で実行」と明記されており、シーケンス図でも `login.html` で完結しています。

- **【第5章 5.4.1 の注記】および【第8章 8.6.1】**
- 「`login.html` 単体ではなく、全画面共通の仕組みとして **`auth.js` の `watchUser()` 内で実行される**」と記載されています。

### 7. 待ち時間の「計算主体」と「データモデル」の矛盾

来場者に表示する待ち時間の算出ロジックと保存先が矛盾しており、第11章の趣旨（実装しない機能の章）とも食い違っています。

- **【第5章 5.4.5】**
- `status.html` 側（クライアント）で「同じ店舗の前方にある注文数から計算」すると記載。

- **【第11章 11.15.3】**
- サーバー側の「Scheduled Function が自動算出し、各店舗の `stores` ドキュメント（**`estimatedWaitMinutes`**）を自動更新する」と記載。（※実装しない機能の章なのに「実装している」と解説されています）

- **【第4章 4.4.1】**
- 第4章の `stores` コレクションのフィールド一覧には `estimatedWaitMinutes` が**定義されていません**。

### 8. 受付番号カウンタの「コレクション名」の矛盾

- **【第4章 4.5.4 / 4.7.4】**：コレクション名は **`counters`** と定義されています。（例: `counters/receipt_pos`）
- **【第9章 9.7.3】**：セキュリティルールのコードブロック内で、コレクション名が **`receipt_counters`** と記述されており一致していません。

### 9. カート情報の「保持場所」の矛盾

- **【第4章 4.5.3】**：「カート情報はブラウザ内の**JavaScript変数にのみ**保持される」と記載。
- **【第6章 6.3.6】**：「カート操作中は、すべての変更が**JavaScript変数およびローカルストレージ**に保持される」と記載。

### 10. モニター画面の「合成音声アナウンス」実装有無の矛盾

- **【第5章 5.5.5 の注記】**：「設計書に記載されていた『合成音声によるアナウンス』は**実装に見当たらない**」と明記。
- **【第7章 7.5.3】**：「ブラウザの Speech Synthesis API を使い、音声でアナウンスを行う」と機能が詳細に解説されたままになっています。
