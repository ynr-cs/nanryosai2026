# 第4章 データ設計（改稿版）

## 4.1 章の目的

本章では，本システムが Firestore 上で管理するデータ構造を定義する。

対象は，ユーザ情報，店舗情報，商品マスタ，注文情報，発番管理情報，同期メタデータである。
あわせて，注文番号の採番方法，注文ステータスの遷移責務，および未実装機能の扱いについても示す。

本章で定義する内容は，実装の都合による一時的な構成ではなく，システム全体で採用する完成形のデータモデルとして記述する。
未実装の機能については，その旨を明記したうえで将来仕様として含める。

## 4.2 Firestore 設計方針

### 4.2.1 基本方針

Firestore のデータモデルは，次の方針で設計する。

* **UI 表示順は明示的な順序フィールドで管理する**
  Firestore は取得順を保証しないため，店舗一覧や商品一覧の順序は `displayOrder` により明示的に制御する。
* **マスタ同期対象は安定 ID を採用する**
  商品マスタはスプレッドシートから同期されるため，商品ドキュメントにはランダム ID ではなく再同期に強い安定 ID を与える。
* **注文ステータスはクライアントから直接更新しない**
  ステータス更新は Cloud Functions を経由し，許可された遷移のみを実行する。
* **番号発番は経路別カウンタで排他制御する**
  POS，モバイル注文，SOK の発番は別管理とし，経路ごとに独立したカウンタドキュメントを持つ。

### 4.2.2 命名規則

本システムでは，Firestore の命名に次の規則を用いる。

* **コレクション名**：複数形・小文字（例：`users`, `stores`, `items`, `orders`, `counters`）
* **フィールド名**：camelCase（例：`displayOrder`, `favoriteItemIds`, `spreadsheetId`）
* **列挙値・ステータス値**：lower_snake_case（例：`ready_for_pickup`, `receipt_mobile`）
* **時刻系フィールド**：原則として `...At`（例：`createdAt`, `updatedAt`, `completedAt`）
  * ただし，既存実装との整合を優先する例外として，`users.lastLogin` はこの命名の例外として採用する。

## 4.4 各コレクションのデータ定義

### 4.4.1 users

`users` コレクションは，認証済み利用者のプロフィールおよび補助情報を保持する。

**`users/{uid}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| displayName | string | 任意 | 表示名 |
| email | string | 任意 | メールアドレス |
| favoriteItemIds | array<string> | 任意 | お気に入り商品のID一覧 |
| termsAgreedAt | timestamp | 任意 | 利用規約同意日時 |
| createdAt | timestamp | 必須 | ユーザ作成日時 |
| lastLogin | timestamp | 任意 | 最終ログイン日時 |

`favoriteItemIds` は，`items` コレクションのドキュメントIDを参照する。
本システムでは商品ドキュメントIDを `{storeId}_{itemId}` で安定化しているため，お気に入り情報も再同期に対して壊れにくい構造となる。

### 4.4.2 stores

`stores` コレクションは，店舗選択画面，商品表示，スプレッドシート同期の基礎となる店舗マスタを保持する。

**`stores/{storeId}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| name | string | 必須 | 店舗名 |
| place | string | 必須 | 出店場所 |
| floor | string | 任意 | 階数情報 |
| displayOrder | number | 必須 | 店舗表示順 |
| spreadsheetId | string | 必須 | 店舗マスタ同期元スプレッドシートID |
| spreadsheetUrl | string | 任意 | スプレッドシートURL |
| isActive | boolean | 必須 | 営業対象かどうか |
| createdAt | timestamp | 必須 | 作成日時 |
| updatedAt | timestamp | 必須 | 更新日時 |

`displayOrder` は，店舗一覧の表示順を安定させるために用いる。
Firestore はデフォルトで表示順を保証しないため，UI 上の順序制御をデータモデル側で明示する必要がある。
`spreadsheetId` は全団体で必須とする。
`spreadsheetUrl` は運用上の利便性のために保持してもよいが，本質的な同期キーは `spreadsheetId` である。

### 4.4.3 store_secrets

`store_secrets` コレクションは，店舗ごとの秘匿設定を保持する。
ここには API トークンや外部連携に必要な秘密情報を格納する。

**`store_secrets/{storeId}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| createdAt | timestamp | 必須 | 作成日時 |
| updatedAt | timestamp | 必須 | 更新日時 |
| secrets | map | 必須 | 店舗ごとの秘匿設定群 |

本コレクションでは，`updatedBy` は持たない。
監査情報が必要な場合はアプリケーションログまたは管理操作ログで管理する。

### 4.4.4 items

`items` コレクションは，店舗ごとの商品マスタを保持する。

**`items/{storeId}_{itemId}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| storeId | string | 必須 | 店舗ID |
| itemId | string | 必須 | 店舗内の商品ID |
| name | string | 必須 | 商品名 |
| price | number | 必須 | 価格 |
| displayOrder | number | 必須 | 商品表示順 |
| isActive | boolean | 必須 | 販売中フラグ |
| updatedAt | timestamp | 必須 | 更新日時 |

商品ドキュメントIDを `{storeId}_{itemId}` とする理由は，再同期時の冪等性を確保するためである。
この構成により，同じ商品が再度同期された場合でも同じドキュメントを上書きでき，重複生成を防げる。
また，`users.favoriteItemIds` からも安定して参照できる。
`displayOrder` は，店舗ごとのメニュー表示順を安定させるために必須とする。

### 4.4.5 orders

`orders` コレクションは，注文そのものを保持する中核コレクションである。

**`orders/{orderId}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| userId | string | 任意 | 注文ユーザID |
| storeId | string | 必須 | 注文先店舗ID |
| orderChannel | string | 必須 | 注文経路 (pos, mobile, sok) |
| receiptNumber | number | 必須 | 受付番号 |
| status | string | 必須 | 注文状態 |
| items | array<map> | 必須 | 注文商品のスナップショット |
| totalAmount | number | 必須 | 合計金額 |
| createdAt | timestamp | 必須 | 注文作成日時 |
| updatedAt | timestamp | 必須 | 更新日時 |
| readyForPickupAt | timestamp | 任意 | 受取可能化日時 |
| lastCalledAt | timestamp | 任意 | 呼出日時 |
| completedAt | timestamp | 任意 | 完了日時 |
| cancelledAt | timestamp | 任意 | 取消日時 |
| abandonedAt | timestamp | 任意 | 放棄扱い日時 |

`status` に入る主な値は次のとおりである。
* `preparing`
* `ready_for_pickup`
* `completed`
* `cancelled`
* `abandoned`

本設計では，決済方式を表す独立フィールドは設けない。
注文の業務状態は `status` を中心に管理する。
また，`monitor.html` はこの `orders` コレクションを参照して表示を行う表示専用画面であり，注文ステータスを書き換える責務は持たない。

### 4.4.6 counters

`counters` コレクションは，受付番号の発番状態を経路ごとに管理する。
本システムでは，発番管理を1ドキュメントにまとめず，注文経路ごとに分割する。

**`counters/receipt_pos`** (他経路も同様の構造)

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| currentNumber | number | 必須 | 直近に採番した番号 |
| minNumber | number | 必須 | 最小番号 |
| maxNumber | number | 必須 | 最大番号 |
| updatedAt | timestamp | 必須 | 更新日時 |

対象ドキュメント：
* `counters/receipt_pos`
* `counters/receipt_mobile`
* `counters/receipt_sok`

この構成により，POS，モバイル注文，SOK の発番を独立させられる。
また，経路別にトランザクション競合範囲を分離できるため，不要な再試行を減らせる。

### 4.4.7 _metadata/master_sync

`_metadata/master_sync` は，スプレッドシート同期の状態を保持するメタデータドキュメントである。

**`_metadata/master_sync`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| status | string | 必須 | 同期状態 |
| lastStartedAt | timestamp | 任意 | 最終同期開始時刻 |
| lastCompletedAt | timestamp | 任意 | 最終同期完了時刻 |
| lastError | string | 任意 | 最終エラー内容 |
| updatedAt | timestamp | 必須 | 更新日時 |

ここでも `updatedBy` は採用しない。

### 4.4.8 banned_users（未実装）

`banned_users` は，将来的に不正利用者の制限を行うためのコレクションである。
現時点では未実装であり，本書では将来拡張のための設計要素として位置付ける。

**`banned_users/{uid}`**

| フィールド名 | 型 | 必須 | 説明 |
|---|---|---|---|
| reason | string | 必須 | 制限理由 |
| createdAt | timestamp | 必須 | 登録日時 |
| expiresAt | timestamp | 任意 | 制限解除予定日時 |

## 4.5 受付番号発番設計

### 4.5.1 発番の基本方針

受付番号は `orderChannel` ごとに独立して発番する。
対象経路は次の3つである。
* `pos`
* `mobile`
* `sok`

各経路はそれぞれ別のカウンタドキュメントを持ち，`createOrder` Function がその値を参照して次の受付番号を決定する。

### 4.5.2 排他制御の基点

受付番号重複を防ぐうえで重要なのは，どのデータを排他制御の基点にするかである。
本システムでは，経路ごとのカウンタドキュメント，すなわち
* `counters/receipt_pos`
* `counters/receipt_mobile`
* `counters/receipt_sok`
を，発番処理の排他制御基点として用いる。

Firestore は明示的な悲観ロック API を提供しないため，実際にはトランザクションによる楽観的排他制御を行う。
`createOrder` は対象カウンタドキュメントをトランザクション内で読み取り，候補番号の探索と注文作成を行ったうえで，同じトランザクション内で `currentNumber` を更新する。
このとき，同一経路で複数の注文が同時に作成されても，同じカウンタドキュメントを read-modify-write するため，一方のコミットが競合で失敗し，自動再試行される。
その結果，同一番号の二重割当てを防止できる。

すなわち，番号重複防止の設計意図は，
**「経路別カウンタドキュメントを発番直列化の基点とすること」**
にある。

### 4.5.3 発番レンジ

発番レンジは次のとおりとする。
* **POS**：100〜999（900件）
* **mobile**：000〜999（1000件）
* **sok**：000〜999（1000件）

番号探索は，直近発番番号の次から開始し，レンジ末尾まで到達したら先頭に戻る循環方式とする。

### 4.5.4 発番探索方式

本システムでは，候補番号の探索を50回固定試行ではなく，レンジ全探索で行う。
理由は，50回固定方式では，レンジ内に空き番号が存在していても，局所的な偏りにより見つからず失敗する可能性があるためである。
したがって，実装では次の件数を上限として探索する。
* **POS**：最大900件
* **mobile**：最大1000件
* **sok**：最大1000件

これにより，レンジ内に空きがある限り，必ずいずれかの空き番号に到達できる。

### 4.5.5 番号占有判定

ある受付番号が使用中であるかどうかは，同一 `orderChannel` かつ終端状態でない注文が存在するかで判定する。
終端状態は次の3つである。
* `completed`
* `cancelled`
* `abandoned`

したがって，占有中とみなすのは主に以下である。
* `preparing`
* `ready_for_pickup`

この方式により，終了済み注文の番号は再利用できる。

### 4.5.6 発番トランザクション手順

`createOrder` Function における発番処理は，概念的には次の手順で行う。

1. `orderChannel` に応じたカウンタドキュメントを決定する
2. トランザクションを開始する
3. カウンタドキュメントを読む
4. `currentNumber` の次からレンジ全体を循環探索する
5. 各候補番号について，占有中の注文が存在するか確認する
6. 空き番号が見つかったら，その番号で `orders` ドキュメントを作成する
7. 同時にカウンタの `currentNumber` をその番号へ更新する
8. コミットする
9. 競合した場合は Firestore の再試行に従う

擬似コードで示すと，以下のようになる。

```typescript
async function createOrder(channel: 'pos' | 'mobile' | 'sok', payload: CreateOrderInput) {
  const config = {
    pos:    { docId: 'receipt_pos',    min: 100, max: 999 },
    mobile: { docId: 'receipt_mobile', min: 0,   max: 999 },
    sok:    { docId: 'receipt_sok',    min: 0,   max: 999 },
  }[channel];

  const rangeSize = config.max - config.min + 1;

  return db.runTransaction(async (tx) => {
    const counterRef = db.collection('counters').doc(config.docId);
    const counterSnap = await tx.get(counterRef);
    const currentNumber = counterSnap.get('currentNumber') ?? (config.min - 1);

    const normalize = (n: number) =>
      n > config.max ? config.min + (n - config.max - 1) : n;

    for (let i = 1; i <= rangeSize; i++) {
      const candidate = normalize(currentNumber + i);

      const q = db.collection('orders')
        .where('orderChannel', '==', channel)
        .where('receiptNumber', '==', candidate)
        .where('status', 'in', ['preparing', 'ready_for_pickup'])
        .limit(1);

      const occupied = await tx.get(q);
      if (!occupied.empty) continue;

      const orderRef = db.collection('orders').doc();
      tx.set(orderRef, {
        ...payload,
        orderChannel: channel,
        receiptNumber: candidate,
        status: 'preparing',
        createdAt: FieldValue.serverTimestamp(),
        updatedAt: FieldValue.serverTimestamp(),
      });

      tx.update(counterRef, {
        currentNumber: candidate,
        updatedAt: FieldValue.serverTimestamp(),
      });

      return { orderId: orderRef.id, receiptNumber: candidate };
    }

    throw new Error('no_receipt_available');
  });
}
```

## 4.6 注文ステータス設計

### 4.6.1 ステータス一覧

注文ステータスは，注文の業務進行状態を表す。

| ステータス | 意味 |
|---|---|
| `preparing` | 調理中・準備中 |
| `ready_for_pickup` | 受け取り可能 |
| `completed` | 受け渡し完了 |
| `cancelled` | 取消済み |
| `abandoned` | 長時間未受取のため放棄扱い |

### 4.6.2 遷移原則

ステータス変更は，クライアントから直接書き込まない。
すべて Cloud Functions を経由して行う。
その理由は次のとおりである。
* 不正な状態遷移を防ぐため
* 更新時刻や関連副作用を一箇所で管理するため
* 管理画面・店舗画面・監視画面の責務を分離するため

Firestore セキュリティルールでは，クライアントによる `orders.status` の直接更新を禁止し，サーバ関数経由のみ許可する構成とする。

### 4.6.3 Function 名付き責務定義

注文ステータスに関与する Function の責務を表4.2に示す。

**表4.2 注文関連 Function の責務**

| Function 名 | 主な呼出元 | 責務 |
|---|---|---|
| `createOrder` | 注文画面 | 注文検証，受付番号発番，初期注文作成 |
| `kitchenComplete` | 店舗操作画面 | `preparing` → `ready_for_pickup` に遷移し，`readyForPickupAt` を記録 |
| `callForPickup` | 店舗操作画面 | 受取呼出を実行し，`lastCalledAt` を更新 |
| `completeOrder` | 受渡操作画面 | `ready_for_pickup` → `completed` に遷移し，`completedAt` を記録 |
| `cancelOrder` | 店舗操作画面 / 管理画面 | 有効注文を `cancelled` に遷移し，`cancelledAt` を記録 |
| `adminUpdateOrderStatus` | 管理画面 | 例外対応として管理者が状態補正を行う |
| `abandonStaleOrders` | スケジュール実行 | 長時間未受取注文を `abandoned` に遷移させる |

### 4.6.4 許可遷移

通常系の許可遷移は次のとおりである。
* `createOrder` により新規注文は `preparing` で作成される
* `kitchenComplete` により `preparing` → `ready_for_pickup`
* `completeOrder` により `ready_for_pickup` → `completed`
* `cancelOrder` により `preparing` または `ready_for_pickup` → `cancelled`
* `abandonStaleOrders` により `ready_for_pickup` → `abandoned`

`callForPickup` は呼出処理であり，通常は `status` 自体を変更せず，呼出時刻の更新を担当する。
`adminUpdateOrderStatus` は例外的な補正機能であり，通常運用の主経路としては扱わない。

## 4.8 本章のまとめ

本章では，Firestore 上で扱う主要コレクションとその役割を定義した。
特に，商品マスタの安定 ID 化，店舗・商品の `displayOrder` 管理，経路別カウンタによる発番分離，および Cloud Functions によるステータス更新統制を，本システムの中核設計として位置付けた。

また，受付番号の発番では，`counters/receipt_pos`，`counters/receipt_mobile`，`counters/receipt_sok` を排他制御基点とすることで，同時注文時の重複発番を防ぐ設計とした。
番号探索はレンジ全探索方式を採用し，局所的な偏りによる発番失敗を回避する。

さらに，未実装機能についても完成形仕様として記述し，将来拡張時にデータモデルの整合性が保たれるようにした。
