# 実装計画: プランC（学校整理番号0014判定）カスタム認証システムへの移行

## 目的

現在の認証システムは **Firebase Auth 標準の Google Sign-In** を利用し、`user.email` のドメイン末尾（`@gl.pen-kanagawa.ed.jp`）で在校生を判定しています。
しかし、このドメインは**神奈川県立全144校に共通**であり、他校生の排除ができません。

プランCでは、Cloud Functions 内でメールアドレスの**先頭4桁が `0014`（南陵高校の学校整理番号）**であることを検証し、**南陵生のみにカスタムトークンを発行**する認証方式に移行します。判定完了後、**メールアドレスは即座に破棄**し、Firebase Auth / Firestore には個人情報を一切保存しません。

## ユーザー確認事項

> [!IMPORTANT]
> ### 設計上の重大な判断ポイント
>
> 1. **スーパー管理者（`ynrcs1000@gmail.com`）の扱い**: このアカウントは `@gmail.com` ドメインのため、プランCの「0014判定」を通過しません。別途 Custom Claims で `role: 'super_admin'` を付与する**専用の管理者認証フロー**が必要です。現行はハードコードで許可していますが、プランC移行後は以下のいずれかの方式が必要です:
>    - **方式A**: Firebase Console から手動で Custom Claims を設定（推奨・最も安全）
>    - **方式B**: Cloud Functions で別途スーパー管理者用の認証エンドポイントを用意
>
> 2. **店舗管理者（`store_admin`）の認証**: 現行のポータルログインでは `@gl.pen-kanagawa.ed.jp` ドメインチェック → パスワード認証で `store_admin` Custom Claims を付与しています。プランC移行後は「0014判定カスタムトークン」でログイン済みの生徒がパスワードで店舗を開錠する方式になります。**教員は利用不可**となりますが、これは設計意図通りでしょうか？

> [!WARNING]
> ### 非互換な変更
>
> - **`user.email` が `null` になる**: カスタムトークン認証では Firebase Auth に `email` フィールドが保存されません。現在 `user.email` を UI 表示や判定に使っている全箇所（後述の11ファイル）が影響を受けます。
> - **`user.displayName` / `user.photoURL` も `null` になる**: Google Sign-In の標準フローではなくカスタムトークンでサインインするため、Google プロフィール情報は取得できません。
> - **`users/{uid}` コレクションの `email` / `displayName` / `photoURL` の保存が不可能に**: `auth.js` の `login()` 内で保存しているこれらの情報は、プランCでは取得元が存在しないため保存できません。

## Open Questions

> [!IMPORTANT]
> ### Q1: ユーザーの表示名について
> プランCではメールアドレス・氏名情報を即座に破棄するため、UIに表示するユーザー名がなくなります。以下のいずれかの対応が必要です:
> - **A**: UID ベースの匿名表示（例: `ユーザー #a1b2`）
> - **B**: ログイン後にニックネームを入力させるフロー追加
> - **C**: 表示名自体を廃止し「ログイン中」とだけ表示

> [!IMPORTANT]
> ### Q2: account.html のメール表示
> 現在 `account.html` ではログインユーザーのメールアドレスと名前を表示しています。プランCではこれらが取得不可となるため、マイページの設計変更が必要です。

> [!IMPORTANT]
> ### Q3: SOK（セルフオーダーキオスク）のフロー
> 現在 SOK はドメインチェック**なし**で全 Google アカウントを許可しています。プランCの「0014判定カスタムトークン」を適用すると、SOK利用者も南陵生限定になります。SOKの対象範囲は変更しますか？
