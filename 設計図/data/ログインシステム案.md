# 南陵祭モバイルオーダー ログインシステム案

## はじめに

本ドキュメントは、南陵祭用モバイルオーダーシステムにおける「校内関係者の識別」と「個人情報の保護」を両立するための認証システム設計案です。
学校側のプライバシーポリシーやセキュリティ要件に応じ、2つのプラン（プランA・プランB）をご提案いたします。

---

## プランA：Cloud Functionsを利用したカスタム認証

### 概要

Googleログインの仕組みを利用しつつ、バックエンド（Cloud Functions）で学校ドメイン（`@gl.pen-kanagawa.ed.jp`）を自動判定します。
判定直後に**メールアドレス情報はシステム上から即座に破棄**されるため、データベース（Firestore）や Firebase Authentication には一切保存されません。

### 処理フロー

```mermaid
sequenceDiagram
    autonumber
    actor User as 生徒
    participant Frontend as ブラウザ(Webアプリ)
    participant Google as Google認証サーバー
    participant Functions as Cloud Functions (裏側)
    participant Firebase as Firebase Auth / Firestore

    User->>Frontend: Googleログインボタンを押下
    Frontend->>Google: 認証リクエスト
    Google-->>Frontend: 認証トークン(IDトークン)を発行
    Frontend->>Functions: トークンを送信 (※Firebaseにはまだ渡さない)

    Note over Functions: 【重要】トークンを開封し、ドメインを確認。<br/>学校アカウントなら「校内ユーザーフラグ」を作成。<br/>判定終了後、メアド情報は【完全に破棄】

    Functions-->>Frontend: カスタムトークン(フラグのみ保持)を返却
    Frontend->>Firebase: カスタムトークンでログイン実行

    Note over Firebase: 管理画面にもデータベースにも<br/>メアドや個人情報は一切保存されない

    Firebase-->>User: ログイン完了（校内ユーザーとして利用可能）
```

### 特徴

| 項目           | 内容                                                                                                                                                               |
| :------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **メリット**   | ・「Googleでログイン」ボタンを押すだけのスムーズなUX<br>・学校ドメイン所持者を確実かつ自動的に識別可能<br>・ハッシュ化処理等を挟むことでさらにセキュアな運用が可能 |
| **デメリット** | ・処理過程で「一時的」にメールアドレスを通過させるため、「取得自体が完全NG」という厳格な校内ルールの場合は抵触する懸念がある                                       |

## プランB：匿名認証とアクセスコード

### 概要

メールアドレスやGoogleアカウントをシステムと一切連携させず、自動発行される「匿名ID」のみでログインします。
その後、Google Classroom等で事前配布されたアクセスコードを入力することで、校内ユーザーとしての権限を付与します。

### 処理フロー

```mermaid
sequenceDiagram
    autonumber
    actor User as 生徒/教員
    participant Classroom as Google Classroom
    participant Frontend as ブラウザ(Webアプリ)
    participant Firebase as Firebase Auth
    participant DB as Firestore

    Note over Classroom, User: 事前にClassroom等で<br/>「校内専用アクセスコード」を告知

    User->>Frontend: アプリにアクセス
    Frontend->>Firebase: 匿名認証リクエスト
    Firebase-->>Frontend: 匿名ID（ランダム文字列）を発行

    User->>Frontend: アクセスコードを入力
    Frontend->>DB: アクセスコードの照合

    alt コードが一致した場合
        DB-->>Frontend: 照合成功
        Frontend->>Firebase: 匿名アカウントに「校内フラグ」を付与
        Frontend-->>User: ログイン完了（モバイルオーダー機能を開放）
    else コードが不一致の場合
        DB-->>Frontend: 照合失敗
        Frontend-->>User: エラー表示（一般来場者画面のまま）
    end

    Note over Frontend, DB: メールアドレス等の個人情報は<br/>最初から最後まで一切システムを通過しない
```

### 特徴

| 項目           | 内容                                                                                                                                                               |
| :------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **メリット**   | ・メールアドレス等の個人情報がシステムを「取得・通過・保存」するプロセスが一切存在しない<br>・**個人情報保護の観点で最も安全であり、学校側の承認を極めて得やすい** |
| **デメリット** | ・初回利用時にアクセスコードを入力する手間が増加する<br>・アクセスコードが漏洩した場合、本当に校内の人間かをシステムで保証できない<br>・個人の特定が難しくなるため、悪質ユーザーへのBAN制度等が事実上機能しなくなる |

---

## 結論と推奨案

- **プランAが適しているケース:**<br>ユーザーの利便性（UX）とシステムとしての確実性（BAN機能やドメインによる本人保証）を重視し、「最終的にデータとして保存されないのであれば、システム内の一時的な処理・通過は許容される」という合意が学校側から得られる場合。
- **プランBが適しているケース:**<br>個人情報の保護を最重要視し、「システム上にメールアドレスを通過させること自体を完全に回避したい」場合。

**まとめ:**
どちらのプランも一長一短があり、**「個人情報の厳密な保護」と「システムとしての安全性・機能性（BAN等の運用）」はトレードオフの関係**にあります。学校としてのコンプライアンス（法令・校内規定）を第一に考えるか、実際の運用上の確実性を取るかでご判断いただくのが最適です。

## 【重要】プランA（カスタム認証）導入に伴うシステム改修の必須要件

現状の南陵祭システムでは、スーパー管理者権限や特定アカウントの識別判定において、フロントエンド各所（9ファイル以上）やCloud Functions内に、特定のメールアドレス（例: `ynrcs1000@gmail.com`）がハードコードされています。

もし学校側のプライバシー要件によって**「プランA」が採用された場合、Firebase Auth上からメールアドレス情報が完全に消滅**するため、現状のハードコードされたメールアドレスによる権限判定（`user.email === "..."`）はすべて機能不全に陥ります。これにより、管理者が誰もログインできなくなる「完全なロックアウト状態（システム全体に及ぶ単一障害点: SPOF）」が引き起こされます。

したがって、プランAを導入する場合は、それとセットで以下の**アーキテクチャの抜本的改修が必須**となります。

### 必須となる改修内容（Custom Claimsへの完全移行）
1. **Cloud Functions側での権限付与**: 
   - Google認証の初回判定用Functions内で、一時的に通過するメールアドレスを元に権限を判定する。
   - 管理者であれば、発行するCustom Tokenに対して `role: 'super_admin'` などの **Custom Claims（カスタムクレーム）** を付与し、その直後にメールアドレス情報を完全に破棄する。
2. **システム全体の判定ロジック書き換え**:
   - `firestore.rules`: 許可条件を `request.auth.token.role == 'super_admin'` へ変更（ハードコードの排除）。
   - フロントエンド全域およびCloud Functions: 定数として設定されているメールアドレスや `user.email` に依存する同期的チェックをすべて削除し、`getIdTokenResult()` を用いて非同期に Custom Claims (`token.claims.role`) を検証する方式へ完全移行する。

**設計上の留意点:**
プランA（メールアドレス非保存）への移行は、単なる認証方法の変更にとどまらず、**システム全体に散らばるメールアドレス依存のロジックを排除し、本来のベストプラクティスである Custom Claims ベースの権限管理へ移行する絶対条件**となります。実装のスケジュールやリソースにおいては、この大規模なリファクタリング（移行コスト）も必ず考慮してください。
