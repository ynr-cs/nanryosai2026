# 南陵祭2026 ファイル設計書

**版**: 1.0
**発行日**: 2026年5月27日
**位置づけ**: 本書はプロジェクト第2層ドキュメント。設計憲法(`design-charter.md`)を上位とし、各ファイルの責務・依存関係・UI操作・運用ルールを定義する。

---

## §0 ドキュメント体系

本プロジェクトのドキュメントは3層構造で管理される。

```
┌─────────────────────────────────────────────────────────────┐
│ 第1層: 設計憲法 (design-charter.md)                          │
│   - API契約・データモデル・ステータス機械・セキュリティルール │
│   - 「システムが何を提供するか」                              │
│   - 唯一の真実の源泉(SSOT)                                   │
└─────────────────────────────────────────────────────────────┘
                            ↑ 参照
┌─────────────────────────────────────────────────────────────┐
│ 第2層: ファイル設計書 (本書)                                  │
│   - 各ファイルの責務・依存・UI操作・運用ルール                │
│   - 「人間がそれをどう実現・運用するか」                      │
│   - 末尾(§99)にファイルに紐付かない運用事項を集約             │
└─────────────────────────────────────────────────────────────┘
                            ↑ 参照
┌─────────────────────────────────────────────────────────────┐
│ 第3層: 設計計画書 (既存)                                      │
│   - 背景・思想・選定理由・読み物                              │
│   - 校長・実行委員・出店団体向け説明資料                      │
│   - 第1層・第2層を引用する側であり、独自決定はしない          │
└─────────────────────────────────────────────────────────────┘
```

**矛盾発生時のルール**:

- 第1層と第2層が矛盾した場合、**常に第1層が正しい**。第2層を修正する。
- 第2層と第3層が矛盾した場合、**常に第2層が正しい**。第3層を修正する。
- 例外なくこの優先順位を守る。

**第2層(本書)の責務範囲**:

- リポジトリに存在する各ファイル(HTML / JS / 設定ファイル / Cloud Functions / 開発スクリプト等)について「何のためのファイルか」「何を呼び、何に呼ばれるか」「どのUI操作を提供するか」を定義する。
- 個別ファイルに紐付かない運用事項(当日のスタッフ体制、障害対応、苦情処理など)は §99 に集約する。
- 第1層が定めた API 契約・データモデル・ステータス遷移を逸脱した記述はしない。
- 散文的な背景説明・選定理由・思想語りはしない(それらは第3層の役割)。

## §1 本書の位置づけ

### 1.1 本書の目的

本書は、南陵祭2026 プロジェクト(`nanryosai-2026/`)に存在するすべてのファイルについて、以下を明示することを目的とする。

- そのファイルが**何のために存在するか**(目的・機能)
- そのファイルが**誰に使われるか**(対象ユーザー)
- そのファイルが**何を呼び、何に呼ばれるか**(依存関係)
- そのファイルが**どのUI操作を提供するか**(画面の場合)
- そのファイルが**現在どこまで実装されているか**(実装状況)

本書を読めば、プロジェクト内のあらゆるファイルの責務・依存・実装状況が即座に把握できる状態を維持する。

### 1.2 本書の責務境界

本書は以下を**書く**:

- 各ファイルの責務・機能・対象ユーザー
- 各ファイルの依存(読み取り・書き込み・呼び出し)
- 各画面のUI操作(設置するボタン・設置しない運用ルール含む)
- 各関数のシグネチャと用途
- 各ファイルの実装状況
- ファイルに紐付かない運用事項(§99 のみ)

本書は以下を**書かない**:

- API 契約・データモデル・ステータス遷移の詳細(第1層で定義済み)
- なぜその設計を採用したかの理由(第3層の役割)
- 校長・実行委員向けの読み物的説明(第3層の役割)
- 個人の感想・思想語り

### 1.3 用語

本書で使用する用語は第1層(設計憲法)の定義に従う。本書独自の用語は導入しない。

### 1.4 改訂方針

- ファイルの追加・削除があった場合、必ず本書の §2 ファイル一覧と該当章を更新する。
- 既存ファイルの責務変更があった場合、必ず本書の該当節を更新する。
- 本書の更新を伴わないファイル変更は禁止する。

## §A 後続AIへの指示書

本書の §3 以降を執筆する後続AIは、以下の指示に厳格に従うこと。

### A.1 守るべき優先順位

1. **第1層(`design-charter.md`)に書かれていることを絶対に逸脱しない**。設計憲法と矛盾する記述を本書に書いた場合、それは本書の誤りである。
2. **§A.4 のテンプレートに従う**。項目の追加・削除・名称変更を勝手にしない。
3. **推測で書かない**。実装ファイルを実際に読み、確認した事実のみを書く。不明な点は **【要確認】** タグを付けて残す。

### A.2 書いてはいけないこと

- 設計の理由・背景・思想語り(第3層の役割)
- 「なぜこの設計にしたか」の説明
- 個人の感想・所感
- 校長・実行委員向けの読み物的説明
- 第1層を書き換える内容(API契約・データモデル・ステータス機械はSSOT)
- 散文的な前置き・まとめ・締めくくり

### A.3 書くべきこと

- 各ファイルの「**何のために存在し、何を担うか**」を超詳細に
- 各ファイルの依存関係(読み取り・書き込み・呼び出し)を漏れなく
- 各画面のUI操作を、設置するものも設置しないものも明記
- 実装状況(完成/部分実装/未実装/削除予定)
- 表示する代表的なエラーパターン(画面の場合)
