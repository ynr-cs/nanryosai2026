## 第1章: 開発背景・変遷の真相・試作段階としての位置づけ

### 1.1 3Dマップ破棄と2D Leaflet V3への転換の「真の理由」
本プロジェクトの初期段階では、Three.js を用いた 3D キャンパスマップ（V1: `main/map_editor/`, V2: `main/map_editor_v2/`, `main/map3d.html`）の開発が進められていました。
しかし、この 3D 構想が中止され 2D マップへと移行した**決定的な理由は、「制作時間とコストパフォーマンスが見合わなかったこと」**にあります。

- **3Dモデリング・空間構築の工数爆発**:
  学校の複雑な校舎形状、傾斜地、階段、渡り廊下、各教室の壁・床を 3D 空間内に正確にモデリングし、テクスチャやライティングを調整し続ける作業には膨大な時間と人的リソースを要します。
- **実用性に対する費用対効果（コスパ）の低さ**:
  来場者が文化祭当日に求める最大の価値は「3Dで校舎を眺めること」ではなく、**「今いる場所から目的の模擬店や教室が何階のどこにあるかを迷わず瞬時に知ること」**です。3D空間の自由回転やピッチ操作はかえって直感的な位置把握を難しくし、制作にかかる膨大な時間に対して得られる実用上のメリットが極めて小さいと判断されました。
- **2D Leaflet + 国土地理院 航空写真への転換**:
  国土地理院が提供する高品質なシームレス空中写真タイルを活用することで、敷地全体のリアルなテクスチャ作成にかかる時間をゼロにし、開発リソースを「実用的な屋内フロア案内」「企画データの検索・連携」「スマホでの快適な操作性」に集中させる方針へ転換しました。

### 1.2 本システムの現状と位置づけ（試作段階 / In-Progress Prototype）
本システム（V3）は、**「設計思想と主要機能の基礎実装を完了し、自動テストによる基礎検証を通過した試作段階」**です。
決して完成形ではなく、実際の運用に向けて以下のような直すべき点・調整すべき課題が数多く存在します：

## 第2章: データアーキテクチャ & Centroid Join（幾何重心自動結合メカニズム）完全解剖

### 2.1 Zero-Remote-Database アーキテクチャ
本システムは、Firestore などのバックエンドデータベースへの通信を一切行わない **Zero-Database 原則** で設計されています。

```
[ 静的幾何資産: campus_map_data.json ]   [ 静的企画カタログ: data.js ]
                  │                                   │
                  └───────────────┬───────────────────┘
                                  ▼ (クライアントサイド結合)
                     [ Leaflet.js V3 地図エンジン ]
                                  │
                   ┌──────────────┴──────────────┐
                   ▼                             ▼
        [ ベクター幾何・部屋描画 ]       [ 動的マーカーピン自動配置 ]
```

- **メリット**:
  1. **超高速・即時起動**: 地図アクセス時に外部サーバーへの認証やクエリ待ちが発生せず、ブラウザキャッシュとCDNによりミリ秒単位で表示。
  2. **完全無料・課金リスクゼロ**: 数千〜数万回のページビューが発生してもFirestoreの読み取り課金が一切発生しない。
  3. **通信障害時の完全自立動作**: 外部APIサーバーがダウンしても、静的アセットさえあればクライアント側で100%動作。

### 2.2 3階層 Centroid Join（幾何重心動的結合）の仕組み
企画データと地図座標をどのように疎結合にし、かつ自動的に正確な位置へピンを立てるかという課題に対し、**Centroid Join（重心結合）** を採用しました。

1. **`main/data/data.js` 側**:
   各企画オブジェクトに `roomId: "room_301"` や `roomId: "tent_a"` という識別子のみを付与する（緯度経度は一切書かない）。
2. **`main/data/campus_map_data.json` 側**:
   各部屋の多角形ポリゴン座標列（`polygon`）や、屋外テントの点座標（`latlng`）に同一の `id` を定義する。
3. **動的重心計算とピン配置**:
   地図読み込み時、多角形ポリゴンの頂点列から数学的な幾何重心（Centroid）を算出し、その座標に企画のマーカーピンを自動生成する。
   同一の部屋に複数の企画が割り当てられている場合（例: 作法室での華道部と茶道部）、同一重心に複数企画が紐付けられ、ボトムシート内でスワイプ切り替えが可能になる。

## 第4章: 管理者用作図エディタ (`map-editor.html`) 実装仕様 & 数学アルゴリズム

### 4.1 アーキテクチャ構成
管理者エディタは、外部依存ライブラリなし（Vanilla JS + Leaflet CDN）で構築されたスタンドアロンWebアプリケーションです。

```
[ MapStudioApp (メインコントローラー) ]
  ├── [ GeometryEngine (幾何計算・スナップ・補間エンジン) ]
  ├── [ HistoryManager (50段 Undo/Redo リングバッファ) ]
  ├── [ UI Inspector & Tree List (属性編集・レイヤー管理) ]
  └── [ Storage & Export Manager (LocalStorage & JSON I/O) ]
```

### 4.2 幾何演算とアルゴリズム
1. **12px 頂点近傍スナップ (`snapToVertex`)**:
   カーソルの緯度経度を `map.latLngToContainerPoint` によりスクリーン座標系 $(px, py)$ に変換し、既存フィーチャーの全頂点とのユークリッド距離 $\sqrt{(x - x_v)^2 + (y - y_v)^2}$ を計算。12px以内の最近傍頂点が存在する場合、その頂点座標に強制吸着させる。
2. **Shiftキー 90度直交拘束 (`applyOrthogonalConstraint`)**:
   直前の確定頂点 $(lat_0, lng_0)$ と現在のカーソル位置 $(lat_1, lng_1)$ に対し、経度差 $|\Delta lng|$ と緯度差 $|\Delta lat|$ を比較。$|\Delta lng| > |\Delta lat|$ の場合は水平線（$lat = lat_0$）、逆の場合は垂直線（$lng = lng_0$）に拘束。
3. **Catmull-Rom スプライン曲線補間 (`interpolateCatmullRom`)**:
   4つの連続する制御点 $P_0, P_1, P_2, P_3$ に対し、パラメータ $t \in [0, 1]$ を用いて滑らかな曲線座標を補間生成（Tension = 0.5）。
4. **LocalStorage 800ms デバウンス自動保存**:
   作図や属性変更が行われるたびにタイマーをリセットし、操作停止後 800ms 経過時点で `localStorage.setItem('nanryosai_map_editor_draft', json)` を実行。高頻度なI/Oによるブラウザのプチフリーズを防止。

## 第6章: セキュリティ & 幾何数値計算の堅牢化（バグ修正の完全解説）

### 6.1 XSS (Cross-Site Scripting) 完全防御
企画データ（`data.js`）、URLパラメータ（`?project=`, `?room=`）、アクセスルート名に悪意ある HTML/JavaScript が混入した場合でもスクリプト実行を阻止する `escapeHtml` 関数を導入し、全動的DOM生成箇所（`innerHTML`, `L.divIcon`）に適用。

### 6.2 浮動小数点桁落ち（Catastrophic Cancellation）の解消
緯度経度座標（約 35.38度, 139.58度）のようなベース値が大きい座標系において、微小ポリゴン（教室サイズ: 差分 0.0001度 程度）の Green の定理外積計算を行うと、有効桁数の減算による桁落ちが発生し、重心が 1km 以上飛散するバグが発生しました。
これを解決するため、**局所原点オフセット（Local Origin Offset）** を導入しました：

```javascript
function calculatePolygonCentroid(coords) {
  if (!coords || coords.length === 0) return CAMPUS_CENTER;
  if (coords.length === 1) return coords[0];
  if (coords.length === 2) {
    return [(coords[0][0] + coords[1][0]) / 2, (coords[0][1] + coords[1][1]) / 2];
  }

  const n = coords.length;
  // 局所原点として最初の頂点を採用（桁落ちを完全防止）
  const x0 = coords[0][0];
  const y0 = coords[0][1];

  let area = 0;
  let cLat = 0;
  let cLng = 0;

  for (let i = 0; i < n; i++) {
    const j = (i + 1) % n;
    const x1 = coords[i][0] - x0;
    const y1 = coords[i][1] - y0;
    const x2 = coords[j][0] - x0;
    const y2 = coords[j][1] - y0;

    const cross = x1 * y2 - x2 * y1;
    area += cross;
    cLat += (x1 + x2) * cross;
    cLng += (y1 + y2) * cross;
  }

  area = area / 2;

  // 面積が極小（退化ポリゴン・同一直線）の場合は単純平均にフォールバック
  if (Math.abs(area) < 1e-12) {
    const sumLat = coords.reduce((acc, p) => acc + p[0], 0);
    const sumLng = coords.reduce((acc, p) => acc + p[1], 0);
    return [sumLat / n, sumLng / n];
  }

  cLat = x0 + cLat / (6 * area);
  cLng = y0 + cLng / (6 * area);

  return [cLat, cLng];
}
```

## 第9章: 今後の改善課題・直すべき点・ロードマップ (To-Do & Future Improvements)

> [!WARNING]
> **試作段階として残されている未解決課題**:
> 本システムは基礎実装を終えたプロトタイプであり、本番稼働に向けて今後直すべき項目が多数あります。以下の課題を順次解決していく必要があります。

### 9.1 現地校舎との実測キャリブレーション課題
- **教室寸法の微細なズレ**:
  現在の教室区画（1F〜5F）は外形ポリゴンからの推定分割でプロットされている箇所があるため、実際の校内図面や現地測量と照合して、壁の位置や廊下の幅を正確に調整する必要があります。
- **生徒棟以外の屋内構造の拡充**:
  体育館（メインアリーナ、サブアリーナ、ステージ位置）、管理棟、特別棟の内部フロアプランがまだ大まかな外形のみのため、展示やステージが配置されるエリアの区画を詳細化する必要があります。

### 9.2 UI/UX・操作感のブラッシュアップ課題
- **スマホ実機でのボトムシート操作感**:
  各種スマートフォン実機（iOS Safari / Android Chrome）において、スワイプ操作時の追従感、フリックでの吸着感、地図ドラッグとの干渉防止をさらにチューニングする必要があります。
- **部屋名・企画名ラベルの視認性**:
  ズームイン時に教室ポリゴン内に表示される部屋番号や企画名テキストが、背景色や文字数によって見づらくならないよう、フォントサイズや折り返し、吹き出しデザインの洗練が必要です。

### 9.3 運用・データ保守フローの課題
- **企画変更の即時反映フロー**:
  直前で店舗名やメニュー、配置場所が変更された際、生徒や管理者が迷わず `data.js` や `campus_map_data.json` を更新できるようにするための運用テストとマニュアル整備が必要です。
